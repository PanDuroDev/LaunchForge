# Phase 1 ownership map and entry gate

- **Status:** Proposed; becomes binding only after the Phase 0 integration owner approves this PR.
- **Phase 1 scope:** MVP only: create/open/save, minimal editor, one renderer, one game entry, standalone portable Windows launcher, and local configured-game launch.

## Required entry conditions

Phase 1 must not start until the integration owner explicitly accepts:

1. ADR-0001 and the Tauri/WebView2 fallback decision.
2. Project schema v1, component contract v1, renderer contract v1, Runtime host boundary, and build request/result contract.
3. Security baseline and the first Windows clean-machine evidence, or a documented waiver naming the accepted residual risk and owner.
4. The exact target Windows baseline, CPU/RAM/display test machine, and dependency/runtime deployment policy.
5. Commit and review a Cargo lockfile generated by the successful Windows build; this PoC does not yet have a resolved lockfile.
6. The remaining Phase 0.3 clean-Windows build/package and preview/export parity gate.

## Integration rules

- One integration owner approves all shared schema, public API, renderer, and build-contract changes.
- Assign one package per agent at a time. Use separate branches and non-overlapping paths.
- If a package requires a contract change, it opens a written proposal with compatibility, migration, tests, and impact; it does not edit the shared contract in the implementation PR.
- P1-B may start against fixtures only after P1-A schema v1 acceptance. P1-C must use the exact same renderer package in preview and export. P1-D may not expose generic shell/filesystem/process APIs. P1-E consumes frozen contracts and must fail closed on security errors.
- P1-F is the integration owner's responsibility and is not delegated as an optional cleanup pass.

## Remaining Phase 0 work before Phase 1

This PR supplies the decision and contract candidates plus a tested host-neutral renderer spike. It does **not** yet include a completed Windows Tauri build result, a fresh-user clean-machine package test, actual WebView2 preview/export visual parity, native startup/memory/CPU/package metrics, or DPI/accessibility behavior. A Windows GitHub Actions build/smoke-test workflow is included, but its result must be reviewed and it does not replace the clean-machine gate. Those remain Phase 0.3 blockers and must be run on a clean supported Windows machine before Phase 1 entry, unless the integration owner explicitly records a waiver.
